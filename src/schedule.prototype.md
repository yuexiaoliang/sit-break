# 日程设置交互原型

这是一次性原型，保存在 `codex/prototype-round-schedules` 分支，用于回答：**“默认安排＋单轮调整”怎样呈现，才能兼顾灵活性和简单易用？**

关联规格：[按轮次推进的自定义日程与休息安排 #1](https://github.com/yuexiaoliang/sit-break/issues/1)。

## 启动

首次检出该分支后安装依赖：

```bash
npm ci
```

启动原型只需：

```bash
npm run prototype:schedule
```

打开 [日程设置原型](http://127.0.0.1:1421/settings.html?prototype=schedule&variant=A)。原型嵌入现有设置页，只在开发环境且显式指定 `prototype=schedule` 时加载；数据全部保存在内存中，刷新即恢复示例。

## 三种方案

| 方案 | 操作结构 | 值得观察的取舍 |
| --- | --- | --- |
| A · 时段卡片 | 每个时段设置默认工作/休息时长，按需展开单轮调整；旁边显示一天概览 | 常规设置集中、特殊设置收起；时段较多时页面会较长 |
| B · 一天时间线 | 先看一天的工作和空档，点击时段，在旁边调整 | 全天关系直观；编辑时需要在时间线与详情间切换注意力 |
| C · 分步设置 | 依次选择日期、时段、单轮安排，最后确认概览 | 每一步信息少；熟练用户回改多个内容时步骤较多 |

同一路由使用 `variant=A`、`variant=B`、`variant=C` 切换。底部浮动条和左右方向键都可切换；输入框、文本框和下拉菜单里的方向键保留原用途。切换布局保留本次编辑的数据。

页面外侧的“查看原型数据”包含当前方案、编辑中的日程、已保存的模拟日程与运行进度，便于核对每次操作。

## 建议试用过程

1. 在 A 中展开上午的单轮安排：第一轮为工作 50 分钟、爬楼 10 分钟；第二轮为工作 55 分钟、深蹲 5 分钟。
2. 把第一轮内容改成多项活动，切换到 B 和 C，观察同一份安排是否容易找到、理解和修改。
3. 点击“试运行”，进入“晚 5 分钟才开始休息”情景；09:55 开始爬楼，仍休息 10 分钟，10:05 进入第二轮。
4. 进入午休边界情景，推进 5 分钟：11:58 已开始的休息到 12:03 完成，然后待机。
5. 推进到下一时段：13:30 从下午第一轮开始，工作 60 分钟再休息 5 分钟。

模拟日为 2026-10-14（周三）；下午结束时间 18:00 是可修改的示例值。总开关关闭时展示原简单计时的设置关系，试运行聚焦日程方式。

## 当前观察

初步推荐 **A 作为后续设计的基础**：符合“先设默认值，再调整少数特殊轮次”的使用方式。B 的全天关系和 C 的首次设置引导，可在用户试用后判断是否需要吸收。

目前确认的是三种结构能表达同一份安排，以及推迟休息、午休衔接能以可见状态演示。**最终方案待用户试用后选择**，不能把上述建议当作用户已经确认的结论。

已进行前端构建和浏览器操作检查，覆盖方案切换、单轮编辑、输入时保留方向键、延迟休息、午休后待机及下午重新开始。生产构建不包含原型界面和切换条。

## 范围与后续处理

此原型不连接真实 Tauri 设置、提醒窗口、系统空闲检测或持久化。退出恢复、真实休眠、随机提示策略及完整跨日行为仍以规格为准；此处保留固定示例提示和按分钟推进的演示时钟。

原型遵循一次性代码约束，没有新增测试框架或业务测试。选定方案后，将确认的界面决策写回规格，正式实现按规格重新组织并验证，保留本分支作为设计依据。
